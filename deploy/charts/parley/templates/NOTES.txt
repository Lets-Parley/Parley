Three things worth knowing:

  * This installed {{ .Values.replicaCount }} replica{{ if ne (int .Values.replicaCount) 1 }}s{{ end }}. Parley supports more than one —
    fanout, presence and the passcode throttle all go through Postgres, and
    migrations serialize behind an advisory lock — but the default is 1 so an
    upgrade never silently doubles your pods. Scale up when you want rollout
    headroom and a survivable node failure:

        helm --namespace {{ .Release.Namespace }} upgrade {{ .Release.Name }} \
            oci://ghcr.io/lets-parley/charts/parley --version {{ .Chart.Version }} \
            --reuse-values --set replicaCount=2

    More than one replica needs chart 0.4.1 or newer; every chart up to and
    including 0.3.0 refuses replicaCount > 1 at render time. At 2 or more you
    also get a PodDisruptionBudget. Every replica opens up to 10 Postgres
    connections plus one for the fanout listener, so size max_connections for
    replicaCount * 11 — 12 per pod briefly at boot, while it holds the
    migration lock on its own connection.

  * Upgrades roll, they do not stop. With more than one replica the rollout is
    seamless; with replicaCount 1 there is a reconnect as the pod is replaced,
    which the client's banner handles.

    During a rollout the new pod migrates the database before the old pods are
    gone, so the old pods run briefly against a newer schema. Parley's
    migrations are additive and that is fine. If an old pod restarts in that
    window it comes back normally, and is replaced by the new version moments
    later. Roll forward, not back.

  * Do not roll back onto an image older than the migrations that have already
    run. Parley will refuse to start rather than corrupt the schema. Restore
    the database from backup first, or roll forward.

## What Parley is

A self-hosted planning-poker and daily-standup tool. One Go binary with the
frontend compiled in, plus a Postgres database. MIT licensed. No SaaS component,
no telemetry, no outbound network calls except to an identity provider you
configure.

- **Deployment**: single container, single replica, enforced.
- **Data**: everything is in your Postgres.
- **Identity**: none by default; optionally any OpenID Connect provider.
- **Access control**: a six-character room code per space.

## The one-paragraph summary

Parley is designed for a team that trusts each other and an operator who does
not want an account system. Its access model is a shared room code, not
identity — anyone holding a code has full participation in that space, and any
member can change or remove that code. The interesting protections are around
*vote secrecy* (strong, and structural) and *not disclosing what exists to
strangers* (also strong). The gaps are concentrated in operations and governance:
no roles, no audit log, no retention or erasure tooling, and no metrics. The
release pipeline publishes an SPDX SBOM and verifiable digest-bound provenance.

If your requirement is "a team of engineers estimates stories without a
third-party SaaS", it fits well. If your requirement is "attributable,
auditable, role-based access to work-planning data", it does not fit yet without
an SSO proxy in front and some SQL of your own.

## Data inventory

| Data | Stored | Notes |
|---|---|---|
| Display name | Yes | ≤64 chars, self-chosen or from an IdP claim |
| Email address | **No** | Used only to derive a name at sign-in, then discarded |
| Password | **No** | There is no local password authentication at all |
| IP address | **No** | No column; used transiently for throttling only |
| Avatar image | **No** | Generated from the name |
| Federated identity | Yes | Issuer + opaque subject, only in `oidc` mode |
| Session tokens | Hashed | SHA-256; the token itself is never stored |
| Room codes | **Plaintext** | Deliberate — see below |
| Session content | Yes | Story titles, notes, votes, standup entries — free text |

## Accepted risks

**Room codes are stored in plaintext.** A code exists to be read off the page and
passed to a colleague. Hashing it would mean no member could look it up again.
The consequence is that a database dump discloses every space's code — which is
why a code is treated as a door, not as an identity.

**Membership is the trust boundary.** There is no finer grain, by design and for
now.

**Anonymous participation is the default.** It is the product.

## Questions a reviewer usually asks next

- *Can we require SSO before anyone reaches a room?* Only by putting an SSO proxy
  in front of the whole instance. `AUTH_MODE=oidc` identifies people, but does
  not gate space access.
- *Can we revoke one person's access?* Not individually. Rotate the room code, or
  delete rows from `session_tokens` to sign everyone out.
- *Can we prove who estimated what?* In `oidc` mode, yes, from the database. There
  is no report and no audit trail; the data is there to query.
- *What happens on a breach of the database?* Everything is disclosed, including
  every room code. Session tokens are hashed, so they are not directly reusable.
- *Is there a disclosure process?* Yes —
  [GitHub security advisories](https://github.com/lets-parley/parley/security/advisories/new).
  Note that **every release before v0.2.2 can be crashed remotely by a
  disconnecting client**, and **v0.1.0 additionally has a throttle bypass**.
  None were retagged; use v0.2.2 or later.

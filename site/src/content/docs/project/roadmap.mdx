Nothing here is a commitment to a date or a scope. This page mirrors
[ROADMAP.md](https://github.com/lets-parley/parley/blob/main/ROADMAP.md) in the
repository, which is the source of truth; the
[issue tracker](https://github.com/lets-parley/parley/issues) has the detail.

## Now

### Spaces you can look after

A space used to be permanent the moment it existed: no rename, no delete, and a
typo in the name was a typo forever. Joining a room meant passing someone a link
and a passcode by hand, and a display name was set once at first sign-in.

Spaces and rooms can be renamed and deleted by the people who own them, a
profile is something you can edit, and an invite is one click rather than two
things copied into a chat window. Merged, awaiting the next release.

## Next

### Switchable poker

A deck becomes something a team chooses and owns rather than a global constant
baked into the server — carried across sessions, with votes that can stay open
and observers who watch without voting.

### Honest ceremonies

Standup carries yesterday's promise into today and asks one question about it:
still on this? An item answered "no" twice running is flagged as stuck — the
item, not the person. And a session can be given a limit, publishing what it did
not get to when the limit runs out.

### Signed links

A capability, not a login: one thing, for one room, expiring. Vote on a story or
add a standup update without first becoming a user the instance has to remember.

### Take the whole instance with you

`parley export` writes every space, session, estimate, vote and standup entry to
a single versioned archive, and `parley import` reconstitutes it elsewhere. Data
ownership is a claim until it is a file you are holding.

### Somewhere for spaces to live

Organizations put a level above spaces, so two teams can both name a room
"Platform Team" and a new starter can find their team's standup without being
sent a link. An organization admin gets custody without access: they can rename,
archive and reassign any space, including private ones, but cannot read a vote,
a standup entry or a note.

Tracking: [#203](https://github.com/lets-parley/parley/issues/203)

### An extensible core

Adding a ceremony to Parley currently means touching the router, a database
constraint, a registry populated at package initialisation, and a ternary in the
frontend. This work makes session kinds a real extension point, so a
retrospective or a story map is code someone adds rather than surgery on the
core.

It pays for itself on other grounds too: it fixes a migration-versioning bug,
gives the two existing kinds one shared authorization path instead of two
reimplementations, and stops an unknown session kind from silently rendering the
wrong room.

Tracking: [#8](https://github.com/lets-parley/parley/issues/8)

## Later

### A plugin system

Extend Parley without forking it — integrations, meeting notes, themes, and whole
ceremonies, installed by the operator and running under capability grants they
approve. Plugin code would be sandboxed WebAssembly with no sockets and no
database access, reaching everything through a host function that checks the
grant first.

Depends on the extensible core.
Tracking: [#9](https://github.com/lets-parley/parley/issues/9)

### The rest of the ceremonies

Retrospectives with grouping and dot voting, action items that outlive the
meeting, user story mapping, a sprint board, async standups, team health checks.

Some of these will arrive as plugins rather than core features, which is rather
the point of the two entries above.

### A collaborative whiteboard

An infinite canvas with sticky notes, shapes, connectors, frames, live cursors
and comments — and every ceremony above able to run on it.

The largest single bet on the page, and one that deserves an explicit decision
before anyone starts: the document engine underneath it is infrastructure, not a
feature.

## Exploring

Ideas under consideration, not committed to:

- Boards that work offline and merge on reconnect
- Retro synthesis and meeting recaps, with a bring-your-own model endpoint so
  nothing leaves the instance
- Two-way issue sync with Jira, Linear and GitHub
- Replaying how a board or a ceremony actually evolved
- Audit logging, retention policies, and SSO group-to-role mapping
- White-label theming

## Things this documentation says are missing

Several gaps named in [Known limitations](/known-limitations/) — membership
roles, account linking, knock-to-join — are on the roadmap in the repository. Others, notably observability and supply-chain tooling, are
not yet scheduled anywhere. That is the honest position rather than an implied
promise.

## Feature requests

[Open an issue](https://github.com/lets-parley/parley/issues/new). Being
discussed does not mean accepted — the status on the issue is the honest signal.

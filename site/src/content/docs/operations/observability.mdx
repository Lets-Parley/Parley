This is a short page, and honestly so.

Parley writes **structured JSON logs to stdout** and emits nothing else. There is
no metrics endpoint, no tracing, no request IDs, and no HTTP access log.

## Logs

One line per event, JSON, at a level set by `LOG_LEVEL` (`debug`, `info`, `warn`,
`error`; default `info`). Collect them the way you collect any container's
stdout.

The single most useful line is emitted at boot:

```json
{"time":"...","level":"INFO","msg":"boot settings","base_url":"https://parley.example.com",
 "cookie_secure":true,"allowed_ws_origin":"https://parley.example.com","port":"8080",
 "auth_mode":"oidc","trust_proxy_headers":true}
```

Almost every "it deploys but does not work" report — cookies not sticking, the
WebSocket refusing to connect, sign-in redirecting to the wrong host — is visible
in that one line. Read it first, before reading anything else.

Beyond boot and database errors, the application logs deliberately little: a
handful of lines around the sign-in flow, and session errors. Parley does not log
request paths, user names, or session content.

## Is that enough?

For this shape of service, mostly yes. Parley is a single replica with no
background workers, no queues and no scheduled jobs. The two questions that
matter operationally are *is the process up* and *can it reach Postgres*, and
both are answered by probing `/readyz` from outside.

What you genuinely lose without metrics is capacity planning — you cannot see
WebSocket connection counts or room sizes without querying the database for
members and sessions. If you are running Parley for a team, that is not a real
gap. If you are running it for an organisation, it is, and it is worth saying so
before you find out.

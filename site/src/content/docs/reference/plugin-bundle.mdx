A plugin ships as one `.parley` file: a deterministic gzip-compressed tar
archive. The full specification, including the byte-level encoding a packer
must reproduce, is `sdk/abi/bundle-v1.md`; golden vectors live beside it in
`sdk/abi/bundle-v1/`.

## Contents

| File | Required | Notes |
| --- | --- | --- |
| `manifest.json` | yes | `package.json` is accepted as a legacy alias, never both |
| `plugin.wasm` | yes | at most **10 MiB** |
| `ui.js` | no | the plugin UI script |
| `slots.json` | no | UI slot declarations |
| `MANIFEST.sha256` | yes | `<hex sha256>  <name>` per file, sorted |
| `MANIFEST.sig` | when signed | Ed25519 public key (32 bytes) then signature (64 bytes) |

A bundle's identity, its **digest**, is the hex sha256 of `MANIFEST.sha256`.

## Signing

The signature is pure Ed25519 over `"parley-bundle-v1\n"` followed by the
`MANIFEST.sha256` bytes. The signer is identified by a **key id** — the first
8 bytes of sha256 of the public key, in hex — which the host computes itself.
Any publisher named in the manifest is ignored.

## What the host refuses

A bundle is refused, before any of it is used, if it contains a file
`MANIFEST.sha256` does not list, lacks a file it does list, or has a file whose
digest does not match; if an entry name has path components, is a symlink or
other non-regular entry, is duplicated, or is not one of the names above; if
`plugin.wasm` exceeds 10 MiB or the uncompressed archive exceeds **16 MiB**
(tar headers and padding included, counted while decompressing), or the
entries' declared sizes add up past it; if anything follows the gzip member; if
`MANIFEST.sha256` is not in canonical form (sorted, lowercase hex, two spaces,
a newline after every line); or if its signature does not verify, is by an
untrusted key, or is missing and unsigned bundles are not allowed.

## The catalogue

Verified bundles are stored in the database, so every replica serves the same
bytes. An admin of the **default** org uploads a bundle on the **Plugin
catalogue** page (`/catalogue`), or with
`POST /api/catalogue/bundles`; nobody else may, including an admin of another
org. Every org member can browse the catalogue, which shows each version's
digest, the signer's key id and what it would be permitted to do.

A bundle is accepted only if it is signed by a key in `PLUGIN_TRUSTED_KEYS`,
or is unsigned and `PLUGIN_ALLOW_UNSIGNED=true`. The first bundle stored for a
name and version holds it: a different bundle for the same name and version is
refused, so a new release needs a new version. Stored bundles are never
deleted.

## Installing by digest

An org admin installs a catalogue version by its digest and key id, and the
install is **pinned** to that row: the host loads it by digest, never by name
and version, so the install runs exactly those bytes, and trust is still
re-checked on every call. The grants, session kinds and consent copy come from
the verified bundle's own manifest. Uploading a `package.json` instead still
works but is deprecated: it resolves to the stored bundle for its name and
version when one exists, and otherwise installs unpinned from loose files.

At boot, after the `PLUGIN_DIR` import, every unpinned install is pinned to the
trusted stored bundle for its name and version, under its own advisory lock.
An install with no match is never disabled: it keeps running from loose files
and the plugins page marks it **not in catalogue**.

Every bundle an install is pinned to is remembered. Going back to an older
version is only possible as a rollback to one of those, and a rollback that
asks for wider grants than the ones in force waits for approval like any
widening upgrade. Because stored bundles are never deleted, every bundle an
install ran stays available to roll back to; retention and garbage collection
of unreferenced bundles are not implemented yet.

`GET /api/catalogue/loaded`, for default-org admins, names the bundles the
answering replica has compiled, by digest and key id, to confirm every replica
runs the same bytes.

A pin is authoritative only while its bundle carries the install's version. An
older binary during a rolling upgrade can change an install's version without
moving its pin; that install then resolves by name and version until the next
boot re-pins it. Avoid plugin admin actions while a rollout is in progress.

`plugin_installs` and `plugin_install_history` hold foreign keys to
`plugin_bundles`, so any future garbage collection has to leave every bundle an
install is pinned to, staged for, or ran (or clear that history first).

## Operator commands

```sh
parley plugin keygen [path-prefix]    # writes <prefix>.key (0600) and <prefix>.pub
parley plugin verify -key <base64-public-key> bundle.parley
```

`keygen` refuses to overwrite either file and prints the key id and the base64
public key to pass to `verify -key`. `verify` accepts `-key`
more than once and `-allow-unsigned`; it prints the digest and key id, or the
reason for refusal, and exits non-zero on refusal. Packing and signing are done
by the plugin SDK, not the server binary.
